## 0. 两条底线（用户定，2026-08-08）

1. agent 必须知道自己在做角色扮演。
2. 一切为剧情、为用户的扮演体验服务——分段是为了让用户有上文可依、让戏不被固化；
   查库是为了世界在用户眼里不漂。手段都要说出目的。

## 1. 三个关键理解

### 1.1 分段的目的：给选择提供上文

分段不是工具纪律，是**交互设计**。用户要参与剧情、要做出选择，前提是手里有上文——
看到一段，知道这一拍演到哪了，才能说「我要往这边走」。一次交完，用户对着完整成品
抓瞎，选择无从谈起。

**每段之间天然存在一个用户介入点。** 这就是分段与 ask 的关系：分段是为 ask 服务的。

### 1.2 计划是假设，不是剧本

beat_plan 不是「列完 → 照单执行 → 勾完收笔」的执行流水线，而是**第一段的起点假设**。
它存在的唯一理由，是给「下一段演什么」一个初始答案。

每演完一段，上文就变了——模型和人一样，**有了新上文就必须重新思考原计划还合不合理**：

1. 演完一段 → 获得这一段带来的新上文
2. 重新评估：原计划剩余几步还成立吗？在上文已经变化的条件下，有没有更好的展开？
3. 成立 → 接着演；不成立 → 重拟 beat_plan（剩下的步重新写，不硬演早先的设想）

「已经写下的戏比计划更算数。」计划是服务于当前上文的临时决策，**剧情永远不被计划锁死**。
这就是分段的目的：不想让剧情固化。一次写完 = 剧情在落笔前就凝固；分段写 = 每一步都
在上文基础上重新活一遍。

### 1.3 ask 接入后：变化是常态，不是例外

ask 接回后，流程可变性是**根本属性**：

- 每段演完 → 用户看到段 → 可能主动接话、可能被 ask 提问
- 用户的回答 = 新上文 = 剧情改道 → **剩余计划当场作废，重拟**
- ask 不是「第 1 轮规划时」的一次性工具——**它是每段之间的常态介入点**：剧情要分岔了，
  停下来给用户 2~4 个选项；用户选了，计划跟着改，继续演。

用户参与选择之后剧情不可能一成不变——ask 的答案每来一次，后面的路就要重走一遍。

## 2. 三层分工（谁也别抢谁的活）

| 层 | 归属 | 职责 |
|---|---|---|
| **思考** | 演员 | 读题（本拍什么处境）、回看（刚写下的那段决定下一段）、评估计划。**不排练正文** |
| **稿纸** | 表演 | 正文唯一入口。一段一段落，落下去就算数 |
| **验收** | 机器 | 字数、禁词、格式、主权程序化判定，违规清单一并回喂 |

三个病根全是抢活：思考里排练（演员抢稿纸）、思考里算字数（演员抢机器）、
一次性交全文（跳过稿纸直接宣读）。

## 3. 一拍之内：按思考轮次的完整流程

### 输入基线（每拍开始前，模型手里已有）

- **常驻系统提示词**（会话内字节稳定）：`# 舞台` → `# 演出节拍` → `# 你扮演的角色` →
  `# 用户扮演` → `# 世界设定（常驻事实）` → `# 叙事与文风` → `# 输出结构` →
  `# 怎么演这一拍` → `# MCP 外设`（可选）→ `# 消息流约定` →
  预设拆层三节（A 原文 / B 文风 / C 边界）→ `# 卡作者附加指令`
- **每拍注入**：【世界状态】→【登场名录】→【活跃面板】→【相关设定】→【设定集索引】→
  【预设末端指令】→【文风与写法】→【行为边界】→【导演备注】
- **用户最新消息** + 历史正文

### 第 1 轮思考——探索与规划（规划轮）

**思考内容**（只许三件事）：读题（谁在场、上文到哪、用户要什么）→ 判型（有戏/没戏）→
构思（有戏则演哪几步）。

**可调用工具**：

| 工具 | 触发条件 | 后果 |
|---|---|---|
| `lorebook_search` | 要写没有十足把握的设定 | `lookups++` |
| `memory_search` | 要带回记不清的人/物/旧账 | `lookups++` |
| `world_state_get` | 拿不准时/地/关系 | `lookups++` |
| `writing_guide` | 预设 D/E 类方法论 | 不打点，结果随拍蒸发 |
| `beat_plan` | 构思完成，列 2~8 条路标（≤60 字/条） | 计划落清单 |

**结束条件**：`beat_plan` 被接受，回执「已记下计划（N 条）……按第一条未完成的写：
draft_append」。到这一行为止，**正文一个字都不许出现**——路标限长是结构性保证
（构思与排练的物理分界）。

**分支**：
- 没戏拍（寒暄/确认/应一声）→ 跳过规划，`draft_write` 一次交完（`lookups==0` 门禁放行）
- 查到的内容与计划冲突 → 重拟 beat_plan 再进入下一轮
- 命中「必须问」（接 ask 后）→ 第一个动作就是 ask，等用户拍板再列计划

### 演段轮循环（真·心脏）

```
演一段（draft_append）
  → 回看刚写的（新上文到手）
  → 评估原计划：还剩的几步还成立吗？
      ├─ 成立 → beat_step_done 勾掉刚演的这条，演下一条
      ├─ 不成立 → beat_plan 重拟剩下几步，按新的演
      └─ 剧情到岔路 → ask 用户 → 答案改道 → beat_plan 重拟 → 按新的演
```

每轮思考新增输入：beat_plan 清单回执（□/☑）+ 现稿 + 工具结果 + 验收报告（未封笔
**无字数读数**）。每轮思考内容：只围绕当前这一段；不看计划全貌、不想后面的段。

写到不确定处才停：查设定/回忆/账本（这时查 → `lookups++`）。

### 收尾轮

- **收笔条件是「戏自然演到停点」，不是「清单勾完」**——哪怕清单还剩两条，只要戏到了
  用户能接话的位置，就可以收
- 通读现稿（需要就 `draft_read` / `draft_search` 定位）
- `draft_seal` 封笔 → 全量验收（此刻才报字数）
- 有违规 → `draft_edit` 定点改（可多轮）→ 自动复验
- `world_state_update` 记账
- 全绿且账已记 → 停止调用 → 正文上屏，停在用户可接话处

### 兜底路径（模型走错时 harness 拉回主线）

- 直出正文 → 引擎代收为 `draft_write`（internal 旁路，不丢正文）
- 一直不落笔 → 催稿「你还没有落笔——用 draft_append 演一段…」
- 查过库却一次交全文 → `draft_write` 门禁拒收：「这拍查过 N 次世界，有戏，一段一段演」
- 思考宣告写尾巴（状态栏等）→ 收尾放行门控多给一轮

## 4. ask 工具接入规范（接回时执行）

旧 ask_director 语义（director.ts 决策门禁）：「必须问」三类——① 用户求方向/递笔
（「怎么办」「给个选项」）；② 用户要生成/定型身份（禁止代写完整档案）；③ 场景岔路
2+ 方向且影响后续多拍。判据：**此刻不定下来剧情就走不下去**（不是「新不新、重不重要」）。

接入位置——**每段之间的常态介入点，重点是规划轮**：

1. 第 1 轮读题命中「必须问」→ 第一个动作就 ask（不落笔、不先演），给 2~4 个具体、
   可落地、彼此不同的选项，等用户拍板
2. 用户回答作为新 user 消息回喂 → 重新构思 → beat_plan 按答案列路标 → 照常演
3. 身份生成：ask 拆成关键选项（出身/职业/性格基调/与主角关系），用户答完再演
4. 演段轮中剧情到岔路 → ask → 答案改道 → 剩余计划重拟 → 继续演
5. 回合末岔路：预设带选择框格式（如 `<w2g>`）时按格式写进正文收尾，不调 ask；
   预设没有选择框才用 ask 工具弹卡
6. ask 的结果改变了剧情输入，应计入「这一拍有戏」的事实（lookups 或单独打点，接回时定）

### 4.1 正文输入与记忆注入（2026-09-18）

- 正文不会把原始角色卡 JSON、小说全文或全部世界书作为单独内容全量发送。压缩前使用当前分支活跃历史；压缩后由 `rp-summary` 接替早期正文，并保留最近正文；只有命中历史回照意图时才追加有限剧情记忆。
- 不新增硬裁剪正常正文历史，以保留剧情连续性。初次 writer 请求的输入构成记录在 assistant details 的 `rpInputComposition` 中，字段包括系统、摘要、历史、动态注入、本拍用户输入、工具 schema 字符数和合计字符数。
- 记忆压缩先完成 evidence/事件写入再追加摘要；周期记忆保存完整 N 拍窗口并带来源锚点，事件命中后可继续回读 Session Tree 原文。

## 5. 任务流程的固定与可变

**固定不变的部分（骨架）**：演一段 → 评估 → 再演。寒暄例外（没戏拍直接交）。
这个顺序不因剧情而变。

**可变的部分（每轮的实际输入与分支）**：
- 读什么：取决于要写什么（设定/记忆/账本/方法论），查不到就模糊带过
- 计划几条：2~8 条，**每段之后都要重新评估，随时重拟**
- 中途分支：查库冲突 → 重规划；必须问 → 先 ask；没戏 → 跳过规划
- 打磨几轮：验收违规才 edit，绿了就停（不做无谓打磨）
- 兜底路径：直出代收、催稿、门禁拒收，全是模型走错时拉回主线

**流程的「固定」靠循环结构，不靠提示词写死步骤**——每轮的「干什么」由工件
（清单/现稿/报告）告诉模型，不由静态文字告诉。剧情永远不被计划锁死。

## 6. 与 opencode 源码机制的对照（2026-08-08 源码研究）

| opencode | 梨园对应物 | 状态 |
|---|---|---|
| plan agent（只读，物理上不能改文件） | 规划轮：只探索+列路标，路标限长 | 结构接近，缺「列完就停」的显式声明 |
| plan_exit 仪式 + build-switch 注入 | 「plan 已接受，开工」切换信号 | **缺失**，模型不知道自己身份已切换 |
| todowrite 存库、每轮回读 | beat_plan 清单随工具结果回传 | 已实现（未提交） |
| 只有真验证过才标 completed | beat_step_done 勾「已交出的段」 | 已实现（未提交） |
| plan-mode / build-switch 每轮动态注入 | 分轮提醒卡（注入层） | **缺失**，流程全在常驻层 |
| 子代理权限 deny | 演段轮不存在写侧以外的工具 | 已实现 |

opencode 与梨园方案几乎同构，但它多了一样梨园没有的东西：**「第 1 轮做完之后，身份
切换这个动作本身是仪式化的」**——plan_exit 要用户确认、build-switch 要注入提醒，模型
明确知道自己现在是什么身份、能干什么。梨园缺的就是这层「现在在第几步」的显式信号。

## 7. 梨园现有系统提示词的问题（对照最终形态）

**核心问题：流程全写在常驻层，注入层不存在。**

- opencode 的流程（plan-mode / build-switch）是每轮动态注入的；梨园把 beat_plan 循环
  写死在常驻系统提示词里，每轮一样。模型从静态段落里猜自己该干什么，而不是从注入
  状态里知道自己该干什么。
- 具体毛病：
  1. 开篇「始终思考剧情的发展和走向」把全貌思考合法化到每一轮（第 1 轮才准想全貌）
  2. 「然后按这个循环演出」把 2、3、4 轮压成一个箭头，模型一口气全干完
  3. 没有「列完清单就停、正文下一轮才开始」的轮次结束条件
  4. 没有身份切换仪式（规划者 → 演员）
  5. 【导演备注】是纪律大杂烩（语言/篇幅/停拍/状态栏/思考用法混在一起），
     一个提醒只办一件事的原则被违背
  6. 机械纪律（「不要在思考里逐条自查」）在四处重复出现，强调通货膨胀

## 8. 预设与提示词的关系（内容供给者 ↔ 流程执行者）

预设经拆层（PRESET-SPLIT-TAXONOMY）按九性质分五去向：A 破限/B 文风/C 边界 → 常驻；
D 方法论/E 场景包 → skill 按需（writing_guide）；F 机械纪律 → 代码；G 验算指令、
H 脑内 harness、I 死块 → 退场/蒸发。

**关系本质：预设 = 内容供给者，提示词 = 流程执行者。拆层把预设里的"机制"全删了
（H 类合计 ~14k 字：COT 系统、七步问题清单、草稿机制、思考≥3500 tokens 教唆），
流程只能由梨园提示词接棒——但梨园自己的流程提示词还没立住。这是「一点进展都没有」
的另一半原因：预设侧拆了，提示词侧没补。**

关系中的问题：
1. **双重真空**：预设的流程指令退场了，梨园的轮次流程又没接住
2. **B/C 常驻不绑轮次**：TGbreak ~2.5k、双人 ~5.2k 的文风+边界每轮在场，
   第 1 轮本该只探索列路标却背着 5k 字内容约束进场
3. **writing_guide「动笔前读」与第 1 轮冲突**：方法论是演段轮的粮食，却安排在规划轮，
   诱发第 1 轮构思人物细节；应改为「演到相关段落时读」
4. **注入层被预设内容占满**：每拍注入全是「内容」，没有给「你现在在第几步」的流程提醒
   留位置
5. **遗留**：A 类破限的 `{{random}}` 破坏前缀缓存（拆层文档 §4.5，未修）

## 11. 8/08 晚修正：演段轮思考塌陷（思考量不足）

**现象（20:00 实弹）**：第 1 轮思考完美（1356/1403 字——理解输入、回顾设定、构思、列路标），
但演段轮思考塌陷为报标题（「开始演第一段」28 字），第 2/3/4 段之间甚至零思考直接连发
draft_append——模型进入「执行流水线」模式，与「每段后重新评估」的目标相反。

**病根**：① 演段回看卡只写了流程分支（勾步/重拟/ask/收笔），没写「这轮思考要想这段的戏」；
② 「不要在思考里起草正文」被过度执行成「思考里不想剧情」；③ 修案又把演段轮窄化为
「只想当前段」，忘记**每段之后是重新评估整个流程**。

**修正（三处措辞，563 绿）**：
1. 演段回看卡（engine.ts roundCardFor）：四问——这段的戏怎么接 / 要不要 ask / 路标要不要重拟 /
   戏到停点了吗，想清楚再落笔
2. 【思考的用法】（assemble.ts）：每演完一段后重新评估「当前段怎么演、要不要 ask、路标是否重拟、
   戏是否到停点」
3. draft_append 描述（tools.ts）：落笔前先在思考里想清这段的戏，并回看已写内容重新评估四问

## 12. 8/08 晚二次修正：注入卡追不上连发，改硬件级门禁

**现象（20:13 实弹）**：首次思考又膨胀到 3034 字（完美时 1356/1403）；演段轮思考仍是
29/24/65 字报标题，第 2/3 段之间零思考连发——**四问措辞完全没生效**。

**根因一（首次思考膨胀）**：四问被写进了【思考的用法】——它是**每拍都在的静态注入**
（buildStageInjection，规划轮也在场），分轮职责泄漏给第 1 轮，模型第一轮就开始想
「当前这段怎么演」。分轮职责只准进 roundCardFor（appends>0 才注入）。

**根因二（演段轮无效，验证后确认卡已注入但模型无视）**：注入卡是「说给模型听」的弱
约束；模型**一轮生成里连发多个工具**（append+done+append），卡只在下一轮 stream 前
注入，**永远追不上它的手速**。opencode 的 plan-mode 能生效靠的是 plan/build 权限硬
隔离，不是提示词自觉。

**修正（对齐 opencode 硬件级控制）**：
1. 【思考的用法】退回纯纪律（思考与正文分界 + 机械纪律归验收器），分轮职责全部移除
2. **同轮连发门禁（engine.ts）**：一轮生成里只允许演一段——本轮已 append 过后再来的
   draft_append 拒收，回喂四问，强制模型停下思考、下一次生成再落笔。回看→评估→再演
   必须在两次生成之间发生，不能靠工具连发绕过。拒收段若已流式上屏，同步触发 `onDraftResync`
   以工作区权威稿件撤掉未受理段；拒收次数计入 `appendRejects` 供演出回放诊断。
3. 新增测试：同轮两个 append → 第二个被拒收（564 绿）
